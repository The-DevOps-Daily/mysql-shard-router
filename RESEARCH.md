# Sources for the post (collected 2026-10-12)

YouTube: https://vitess.io/docs/overview/history/ ("created in 2010 to solve the MySQL scalability challenges"; write traffic too high for the primary -> shard; proxy between app and DB). Connection memory 256KB to ~3MB per MySQL connection: https://vitess.io/docs/overview/whatisvitess/ . Sugu QCon 2018 "MySQL is not good at handling too many connections" https://www.infoq.com/presentations/vitess/ . First resharding "took an entire night of master downtime" https://www.percona.com/blog/2016/03/10/percona-live-featured-talk-with-sugu-sougoumarane-vitess-the-complete-story/

Slack (2020-12-01) https://slack.engineering/scaling-datastores-at-slack-with-vitess/ : workspace-per-shard; shard hit largest hardware; hotspots + underutilized fleet; re-keyed messages by channel id; 2.3M QPS peak (2M reads, 300K writes), median 2 ms, p99 11 ms; 99% of Slack MySQL traffic; migration fall 2016 -> end 2020; double-writes + double-read diffing.
Slack incident 2022-02-22 (post 2022-04-26) https://slack.engineering/slacks-incident-on-2-22-22/ : keyspace sharded by user, query without sharding key -> scatter to every shard.
Slack hot shard (2023-11-15) https://slack.engineering/the-query-strikes-again/ : one shard held 6% of user subscription data; OOM-killed MySQL on shard primary.

GitHub (2021-09-27) https://github.blog/engineering/infrastructure/partitioning-githubs-relational-databases-scale/ : mostly vertical partitioning by schema domain; linters; 2019 mysql1 950k QPS avg (900k replicas, 50k primary); 2021 1.2M QPS, avg host load halved; moved 130 busiest tables at once; Vitess vertical sharding to move tables without downtime.
GitHub MySQL 8 (2023-12-07) https://github.blog/engineering/infrastructure/upgrading-github-com-to-mysql-8-0/ : 1200+ hosts, 300+ TB, 5.5M QPS, 50+ clusters; horizontally sharded Vitess clusters for large domains; upgraded one shard at a time.

Shopify Shop app (2024-01-17) https://shopify.engineering/horizontally-scaling-the-rails-backend-of-shop-app-with-vitess : user_id sharding key; removed all cross-shard transactions (partial commit risk).
HubSpot (2022-01-13) https://product.hubspot.com/blog/improving-reliability : 750+ Vitess shards per DC, ~1M QPS, 3-instance MySQL per shard, on Kubernetes.
Cash App (2018-11-07) https://developer.squareup.com/blog/sharding-cash/ : entity groups stay together; first split < 1 s downtime.
